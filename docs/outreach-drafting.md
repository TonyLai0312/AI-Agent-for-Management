# Live outreach drafting

The selected-company live workflow supports connection requests, LinkedIn follow-ups, email drafts and warm reconnection. It preserves the existing application and demo workflow. No endpoint sends outreach.

BDR must confirm the current contact, industry, approved customer reference or explicit no-reference decision, and existing invitation/connection status. The server derives the channel: new → connection; accepted/existing connection → LinkedIn; checked/pending → email; declined → stop; wrong contact → rediscovery with contact, industry and reference decisions cleared. Status is retained under normalized person + company identity across repeated contact entries. Existing or previously sent invitations cannot be reset to new. A late status update invalidates unsent drafts; a concurrent update discards in-flight generation.

Warm reconnection additionally requires dated BDR-supplied relationship history with reviewer, confirmation date and note. Changing/removing history invalidates drafts. History is supplied to the model only for a warm request. Generated messages cannot research or browse: the structured Responses request receives confirmed identity/role/industry, the exact approved customer claim and entity/application/geographic scope, and optional confirmed history. Technology preferences and unverified market signals are not supplied. Instructions require concise natural business English, a role-relevant question and no invented facts. Deterministic validation rejects changed customer claims, unknown numerical claims, unsolicited URLs/emails, common unsupported relationship assertions and technology names. These checks do not prove arbitrary prose is factual; BDR must attest that every sentence is supported before approval.

The per-company connection limit defaults to 300 Unicode code points and is configurable from 50–1,000. Final personalized text is counted with `Array.from(text).length` on the client and server. Generated overlong text gets up to two full-sentence rewrite requests (three total Responses calls), within existing timeouts, SDK retry and admission limits. Persistent overlength fails explicitly. Edited overlong text is rejected; no truncation occurs.

Each generation/edit creates a version with parent, text, contact identity, channel, model/response provenance, creation time, limit and approved-support snapshot (claim, source URL where available, approver and date). Edits clear approval. Only the latest valid version can be approved, copied or recorded as manually sent. Copy revalidates the server's current evidence/status/version and approval. Older versions remain visible. Existing pre-feature drafts are retained as invalidated history.

An actual manual-send record stores the exact approved text/version, channel, contact, BDR, actual send timestamp and separate recording timestamp. Send time must follow approval and cannot be in the future. Recording an invitation marks it pending, blocking another invitation. Generating, approving and copying never create a send record. Records survive demo resets.

Validation passed: 54 unit/database/adapter tests (`npm test`), `npm run typecheck`, `npm run build`, 14 browser workflow scenarios, and the separately isolated missing-key browser test (15 browser scenarios exercised in total). QA uses explicitly synthetic data only in disposable `work/` databases; injected provider callbacks exist only in tests.
